<objective>
Close the 3 confirmed critical gaps recorded in `05-VERIFICATION.md` (independently corroborated by `05-REVIEW.md`) that are currently blocking Phase 5 from being marked complete:

- **CR-01** — the client never distinguishes a server-side auth/DB failure from "no subscription," breaking the fail-closed guarantee both `05-01-PLAN.md` and `05-02-PLAN.md` document as a must-have.
- **CR-02** — the Billing history table duplicates every invoice once per held product, because the server's intentionally shared invoice list gets flattened across all held products client-side.
- **CR-03** — `cancelAtPeriodEnd` is fetched live from Stripe but never rendered, so a subscriber who cancelled but is still inside their paid period gets no indication the cancellation took effect.

These are 3 independent, narrow corrections to already-shipped, already end-to-end-wired code (05-01's server endpoints, 05-02's client hooks and `Account.jsx`) — not new feature surface. There is no new vertical slice to prove end-to-end for the first time; the slices already exist and are already wired. This plan therefore uses 3 focused `auto` tasks (one per confirmed gap) rather than a tracer/expansion split.

Purpose: Make Phase 5's own headline promises (ACCT-01: real, accurate status/renewal; ACCT-02: a cancellation is visible after the fact; ACCT-03: accurate invoice history) actually true — closing the gap between what `05-01-PLAN.md`/`05-02-PLAN.md` documented as must-haves and what the shipped code actually does — **without** regressing Phase 3/4's already-verified signed-out behavior on `/subscribe`, `/subscribe/success`, or `/editions/:no`, all of which share the `src/lib/useSafeFetch.js` primitive that Task 1 modifies. That shared-primitive blast radius is exactly what the naive version of the CR-01 fix (throwing on every non-2xx status, including 401) would break, so Task 1's design and verification explicitly account for it.
