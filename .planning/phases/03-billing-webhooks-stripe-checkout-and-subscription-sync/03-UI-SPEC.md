## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — plain CSS (`src/styles/eclat.css`), hand-rolled utility/component classes |
| Icon library | none — hand-drawn inline SVG (matches the existing hamburger toggle in `Header.jsx` and the checkmark tick in the current `Subscribe.jsx` "done" state); this phase reuses that checkmark for the success view and reuses the existing `.dot` pulse (hero scroll indicator) for the confirming/loading state — no new icon asset is introduced |
| Font | `--serif` Bodoni Moda (display/headings, unchanged), `--sans` Archivo (body text, tile copy), `--narrow` Archivo Narrow (uppercase labels/eyebrows/badges) — all three already declared in `src/styles/eclat.css` `:root`, none new this phase |

**shadcn gate note:** `components.json` was not found, and no Tailwind config exists in this repo. This project has an established, deliberate bespoke design system (`src/styles/eclat.css`, ~2000 lines, editorial serif/narrow-sans type system, custom `--accent`/`--ok` oklch tokens) that predates this milestone and is explicitly the system to *extend, not replace* per `CLAUDE.md` and this phase's own brief ("feels native to the existing site rather than introducing a new design language"). shadcn was evaluated per protocol and declined — introducing a Tailwind/Radix-based component system for a single product picker and a confirmation view would fragment the design language for no benefit, and would require rewriting the site's plain-CSS build pipeline. All contract values below extend the existing tokens/classes in `src/styles/eclat.css` rather than inventing a parallel system. This mirrors the identical decision already made and approved in `02-UI-SPEC.md`.

**Blocking dependency this contract cannot resolve (not a UI decision, a data precondition):** RESEARCH.md Open Question 1 (D-02) — whether each of the 4 Stripe products has one fixed price or separate monthly/annual prices — is unverified as of this writing. This contract specifies a tile layout that accommodates **either** shape (see Phase-Specific Component Notes §1 and UI Considerations row 14) rather than assuming one. The real shape must be confirmed against the live Stripe account before the picker's markup is finalized; until then, treat the "single price" rendering as the default and the "price + interval toggle" rendering as the fallback this contract also specifies.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Gap between the "Subscribed" badge and its checkmark glyph |
| sm | 8px | Gap between a tile's price line and its optional interval sub-line |
| md | 16px | Gap between product tiles in the picker grid; inline error-banner internal padding gap |
| lg | 24px | Confirming/success view internal vertical rhythm between icon → heading → body |
| xl | 32px | Space between the last product tile row and the page-level error banner above it |
| 2xl | 48px | Vertical gap between the picker heading block and the tile grid |
| 3xl | 64px | not used this phase |

Exceptions: the existing codebase does not strictly follow an 8-point scale (e.g. `.plans` grid `gap` is `18px`, `.plan` padding is `28px`, `.total-row` `padding-top` is `26px`, `.eyebrow` bottom margin is `18px`). This phase's reworked picker **reuses these exact existing values verbatim** (the `.plans`/`.plan` classes are extended, not replaced — see Component Notes §1) rather than nudging them onto the 8-point grid, so the new picker sits visually flush with the rest of the already-shipped page chrome. Only genuinely new spacing decisions (the badge/checkmark gap, the confirming-view rhythm, the error-banner spacing) use the declared scale above.

## Phase-Specific Component Notes

Concrete visual/interaction specs for the reworked `/subscribe` route and the new `/subscribe/success` view. These are prescriptive — implement as specified, not as a starting point for redesign.

### 1. `/subscribe` product picker (replaces the current two-step monthly/annual flow)

Removes `Subscribe.jsx`'s current `step` state machine (`plan` → `pay` → `done`) entirely — there is no multi-step wizard anymore, because Stripe's hosted Checkout page is the payment step (D-03). The page becomes a single view: a heading block followed by a 4-tile grid, each tile independently actionable.

- **Layout:** reuse the existing `.plans` grid (`display: grid; grid-template-columns: repeat(auto-fit, minmax(260px,1fr)); gap: 18px;`) unchanged, now holding exactly 4 `.plan`-derived tiles instead of 2.
- **Tile anatomy** (extends `.plan`, `.plan__row`, `.plan__name`, `.plan__price`, `.plan__note` — all unchanged base classes):
  - `.plan__name` — product name (`Éclat Online`, `Éclat Hard Copy`, `Children's Book Online`, `Children's Book Hard Copy`), wraps onto two lines, never truncates (see UI Considerations row 6).
  - `.plan__price` — real Stripe price, e.g. `$9` — sourced from a live server read (`GET /api/billing/status` or a companion prices endpoint), never from `SITE.price` (BILL-02).
  - **New** `.plan__interval` (sub-line under price, 13px/`var(--muted)`, `sm` token gap above): renders `/mo` or `/yr` if D-02's research confirms a single fixed interval per product, OR renders a small inline toggle (two `.chip`-style pills, reusing the existing `.chip`/`.chip[aria-pressed]` pattern from `Archive.jsx`) if D-02 confirms multiple intervals exist. Reserve this line's height either way so the tile's overall height doesn't jump once the real shape is confirmed.
  - **New** `.plan__badge` (only rendered when the signed-in user already holds this product, D-04): a small accent-filled pill, reusing `.pill`'s visual treatment but filled (`background: var(--accent); color: #fff;`) rather than outlined, label "Subscribed", positioned top-right of the tile via `.cover__badge`'s absolute-corner pattern adapted to the tile's own `position: relative`.
  - **Action area:** unowned tile → a `.btn` labeled "Subscribe" that is a plain link-style GET navigation to `/api/billing/checkout?product={key}` (full browser navigation, not a fetch — same "no JS interception" principle as `02-UI-SPEC.md`'s Sign-in link, Pitfall 1's lesson generalizes). Owned tile → a `.btn.btn--ghost` labeled "Manage" linking to `/account` (React Router `<Link>`, in-app navigation is fine here since no OAuth/redirect chain is involved).
- **Query-param preselect (D-08):** if `/subscribe?product=eclat-online` (or similar) is present on load, that tile gets a `2px solid var(--accent)` border (distinct from the `.plan[aria-pressed='true']` selected-state border, which is `var(--ink)` and no longer used here since there's no click-to-select step) and is scrolled into view via `scrollIntoView({ block: 'center' })` on mount. This does not auto-trigger checkout — the user still clicks "Subscribe" themselves.
- **Per-tile entitlement loading:** until `GET /api/billing/status` resolves, every tile's action area renders a skeleton pill (same box dimensions as the eventual `.btn`, `background: rgba(22,19,15,0.06)`, no text, subtle `opacity` pulse reusing the `pulseDot` keyframe's easing) instead of guessing "Subscribe" first.
- **Entitlement fetch failure:** every tile falls back to "Subscribe" (safe default per D-04's server-side re-check) plus a single small inline notice below the grid heading, 13px/`var(--faint)`, non-blocking: "Couldn't confirm your current plans — refresh to check."
- **Checkout-creation failure:** a `.demo-notice`-shaped banner (same structure, swap `--accent` for the new `--bad` token in border/tag background) appears above the grid: tag "Error", body "Something went wrong starting checkout — try again." The failed tile's own "Subscribe" button is unaffected/re-clickable.
- **Page heading:** keep the existing `.eyebrow` + `.display` header block structure ("Subscribe to Éclat" / lede paragraph) — only the content below it changes from the two-step wizard to the single grid.

### 2. `/subscribe/success` confirming → success/timeout view (new route, D-06/D-07)

New route (add to `src/App.jsx`, `src/data/seo.js` `staticSeo`/`allRoutes()` per the existing three-places-in-sync convention noted in codebase architecture). Reuses the existing `.done` centered layout exactly (`text-align: center; padding: 60px 0;`) from today's `Subscribe.jsx` "done" step — same container, three possible content states inside it:

- **Confirming (initial, always shown first):** the existing pulsing `.dot` (accent-colored, already has a `pulseDot` keyframe animation from the hero scroll indicator) centered above the heading, sized up to ~14px via inline style, replacing the current checkmark SVG for this state only. Heading "Confirming your subscription…" (`.display`, same size/weight as today's "You're in."), body "This usually takes a few seconds." (`.lede`). Polls `GET /api/billing/status?product={key}` every ~2 seconds.
- **Success (poll finds the row):** swaps the pulsing dot for the existing checkmark-tick SVG (exact markup already in `Subscribe.jsx`'s current "done" step — reuse verbatim, do not redesign). Heading "You're subscribed." Body per Copywriting Contract's product-aware line. Two `.btn`/`.btn--ghost` actions in a `.btn-row`, centered: a primary link to the relevant content area (Online products → `/archive` or `/books`; Hard Copy products → `/account` only, since there is no digital content to open) and a secondary "Account" link to `/account` — mirrors today's existing "Open the archive" / "Account" button pair exactly.
- **Timeout (poll exceeds ~20–30 seconds without a row appearing):** swaps to a neutral state — no checkmark, no error icon, just the `--bad`-colored heading text "This is taking longer than expected." and body "Check your email for a receipt, or view your account — this page will keep checking in the background." with an inline `.btn--ghost` link to `/account`. Polling does **not** stop on timeout — it keeps running at a longer interval in the background in case the webhook is merely delayed, per D-07's rule that only the webhook-synced row counts, never a client-side assumption.

## UI Considerations

Applicable state considerations resolved: 5 covered, 6 backstop, 1 unresolved (2 dismissed with reason)

*(Ran through the `ui-consideration-probe` engine per the standard state-coverage gate. The product picker is a genuine per-user async surface — unlike Phase 2's fixed-content nav slot — so `loading`/`error`/`populated` all meaningfully apply here, not just to a nav control. `empty` and `partial` are dismissed below because the catalog itself is fixed, even though the entitlement data layered on top of it is live.)*

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | product picker (`list-collection`, 4 tiles) | dismissed | The catalog is a fixed set of exactly 4 real Stripe products, hard-coded server-side (RESEARCH.md Pattern 1 allowlist) — never fetched as a variable-length list, so a zero-product empty state is not reachable |
| partial | product picker (4 tiles) | dismissed | Each tile is atomic, not partially filled in — a tile renders either its full skeleton-loading placeholder or its fully-resolved state (name, price, subscribed/not), never a mix of resolved and unresolved fields on the same tile (see loading row below) |
| populated | product picker (4 tiles) | ✅ covered | Happy path renders all 4 tiles with real price/interval data and correct per-product Subscribed/Subscribe state once `GET /api/billing/status` resolves |
| overflow | product picker (4 tiles) | ✅ covered | Reuses the existing `.plans` auto-fit grid so 4 tiles reflow 2-up then 1-up on narrow viewports without horizontal scroll or clipping — same proven pattern already on `/subscribe` today |
| zero-one-many | product picker (4 tiles) | ✅ covered | Per D-05, a user may hold 0, 1, or up to all 4 subscriptions simultaneously; each tile's badge/action state is independent — no page-level copy implies a bundled or all-or-nothing plan |
| long-text | product tile name (`static-content`) | ✅ covered | Product names (longest: "Children's Book Hard Copy") wrap onto two lines via `.plan__name`'s existing serif treatment rather than truncating; tile height is intrinsic, not fixed |
| long-text | Subscribe/Manage button label (`interactive-control`) | ✅ covered | Button copy is fixed-form and short ("Subscribe" / "Manage") — never variable-length user or product data that could wrap awkwardly inside the pill-shaped `.btn` |
| loading | product picker — per-tile entitlement state | 🧪 backstop | While `GET /api/billing/status` is in flight, every tile's action area shows a skeleton placeholder (same box size as the eventual button) instead of flashing "Subscribe" then swapping to "Subscribed" |
| error | product picker — entitlement fetch failure | 🧪 backstop | If `GET /api/billing/status` fails, every tile falls back to its default "Subscribe" action plus a small inline notice — safe because the server-side Checkout-creation endpoint independently re-verifies no active subscription exists before creating a session (D-04), so a stale "Subscribe" render can never cause a duplicate charge |
| loading | Subscribe button (per tile, on click) | 🧪 backstop | Clicking "Subscribe" is a real server redirect (`GET /api/billing/checkout`), not a fetch; the clicked button immediately enters a disabled/`aria-busy` visual state to prevent a double-click firing two redirect requests while the browser navigates away |
| error | Subscribe button — checkout-creation failure | 🧪 backstop | If `/api/billing/checkout` responds with an error instead of a 302 (unknown product key, expired session), the picker shows the `--bad`-colored inline banner ("Something went wrong starting checkout — try again.") — no silent failure, no dead click |
| loading | `/subscribe/success` confirming view (D-06) | 🧪 backstop | Shows "Confirming your subscription…" with the pulsing `.dot` while polling `GET /api/billing/status` every ~2s — the unlocked/success view never renders before the webhook-synced row is actually observed (D-07) |
| error | `/subscribe/success` — poll timeout | 🧪 backstop | If polling exceeds ~20–30s without the row appearing, the view swaps to the distinct timeout state (Component Notes §2) and keeps polling in the background — never spins indefinitely, never silently reveals the success view as a timeout fallback |
| long-text, overflow | price + billing-interval display (per tile, `static-content`) | ⚠ unresolved | Whether each product has one fixed price or separate monthly/annual prices is UNVERIFIED (RESEARCH.md Open Question 1 / D-02) — Component Notes §1 specifies a layout (`.plan__interval` line, optional chip toggle) that fits either shape, but the real shape must be confirmed against the live Stripe account before this element's markup is finalized; planner must treat this as an execution-time blocking task, not silently assume single-price |
