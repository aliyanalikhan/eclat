<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> api/auth/google.js | Untrusted client request (query string `return_to`) crosses into server code that constructs a redirect |
| Browser -> api/auth/google/callback.js | Untrusted client request (`code`, `state` query params, `oauth_state`/`oauth_return_to` cookies) crosses into server code that exchanges a code for tokens and creates a session |
| Server -> Google OAuth/JWKS endpoints | Server-to-server token exchange and JWKS fetch; the response is only trusted after independent JWT verification, never assumed correct by transport alone |
| Server -> Postgres (users/sessions) | Server writes identity and session data; a DB compromise/leak is mitigated by only ever storing a hash of the session token, never the raw value |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Spoofing | api/auth/google/callback.js | critical | mitigate | jose jwtVerify against Google's live JWKS, checking signature + audience (GOOGLE_CLIENT_ID) + issuer + expiry, before any user/session row is created (D-03/AUTH-02) |
| T-02-02 | Tampering | api/auth/google/callback.js | high | mitigate | state-cookie double-submit: the `state` query param must exactly match the `oauth_state` cookie value or the flow aborts before token exchange (RESEARCH.md Pattern 1) |
| T-02-03 | Tampering | api/auth/google.js, api/auth/google/callback.js | medium | mitigate | `isSafeReturnTo()` in lib/session.js rejects any `return_to` that is not a same-origin relative path, closing the open-redirect vector |
| T-02-04 | Information Disclosure | lib/session.js, migrations/0002_sessions_token_hash.sql | high | mitigate | Only the SHA-256 hash of the session token is ever written to `sessions.token_hash` (D-12) — a database read or dump alone cannot be replayed as a live session |
| T-02-05 | Information Disclosure | api/auth/google/callback.js Set-Cookie | high | mitigate | Session cookie is set httpOnly (D-13), making it unreadable to any client-side JS even in the presence of an XSS bug elsewhere on the site |
| T-02-06 | Information Disclosure | api/auth/google/callback.js Set-Cookie | medium | mitigate | Session cookie is set Secure (D-13); Vercel serves HTTPS only, so the cookie is never transmitted over plaintext |
| T-02-07 | Spoofing | N/A (flow-shape level) | low | accept | ID-token replay via a browser-visible nonce is not a relevant vector for this server-initiated authorization-code flow — the ID token is only ever seen server-to-server during token exchange, never in the browser (RESEARCH.md Assumption A5; COVERAGE.md nonce_replay_protection row) |
| T-02-SC | Tampering | package.json (jose, cookie installs) | high | mitigate | Both packages cleared by RESEARCH.md's Package Legitimacy Audit (OK/Approved, no SLOP/SUS, no postinstall scripts) — no blocking human-verify checkpoint required per protocol |
